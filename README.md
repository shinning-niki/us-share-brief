# 美股收盘简报（云端自动化）

美东交易日收盘后，北京时间 **早上 4~8 点之间**自动抓取美股收盘数据，生成手机端简报页面并推送到手机。
**全程运行在 GitHub Actions 云端，本机关机不影响。**

调度不是「设个 7:40 的闹钟」，而是**提前排队 + job 内睡到收盘**：cron 设在收盘前
（北京 23:45 / 00:45），job 一旦被 GitHub 调度起来就先睡到美东 16:05 再干活。
这样 cron 的队列延迟被睡眠抵消，送达时间恒定在收盘后几分钟。详见下文「调度」。

这是 [a-share-brief](../a-share-brief) 的美股版：**同一套方法论，按美股的市场结构换了变量**。

## 为什么是云端

WorkBuddy 内置定时任务绑定在本机进程上，电脑休眠/关机即停止调度。
本项目把调度、取数、渲染、推送全部搬到 GitHub Actions，唯一的本机依赖是首次部署。

## 调度：为什么不能只靠 cron 定时

### 实测事实

GitHub Actions 的 `schedule` 是 **best-effort**：会延迟，会被静默丢弃，没有任何补偿机制。
这不是推测，是三个仓库的完整调度历史统计出来的：

| 仓库 | cron 设定（UTC） | 实际执行（UTC） | 偏差 |
|---|---|---|---|
| us-share-brief | 10-20 23:40 | 10-21 01:58 | **晚 2h18m** |
| us-share-brief | 10-21 23:40 | 从未出现 | **丢失** |
| a-share-brief | 07:20 / 07:45 / 08:15 / 08:50 / 09:30 | 只有 14:10 和 14:35 跑了 | **晚 6h50m，5 个丢了 3 个** |
| trend-dashboard | 11:00 / 12:00 / 13:00 / 14:00 / 15:00 | 散布在 15:23 ~ 20:33 | **0.5 ~ 5.5 小时** |

最后一行最关键：`trend-dashboard` 的 5 个整点 cron，实际执行时刻在一个 5 小时的
区间里随机散布。**没有任何 UTC 时段是可靠的**——换时段解决不了问题。

### 解法：提前排队 + 睡到收盘

原来的设计把 cron 设在收盘后（北京 07:40），距离「8 点送达」只有 20 分钟余量，
延迟 2 小时就直接跨过去。**cron 越靠近送达时限，容错空间越小。**

反过来做：cron 设在**收盘前**，job 一起来就先睡到美东 16:05。

```
北京 23:45 准点起跑    → 睡 4h20m（夏令时）/ 5h20m（冬令时）→ 04:05 干活 → 04:10 送达
北京 23:45 延迟 3 小时  → 02:45 起跑 → 睡 1h20m → 04:05 干活 → 04:10 送达
北京 23:45 延迟 5 小时  → 04:45 起跑 → 已收盘不睡 → 04:45 干活 → 04:50 送达
```

队列延迟被睡眠抵消，送达时间恒定。**容错空间从 20 分钟变成 5 小时。**

代价是 job 要睡几小时。仓库是 public，Actions 分钟数完全免费且不限量
（2000 分钟/月的限制只对私有仓库生效），所以这个代价是零。

### 13 个触发点，三层

| 层 | UTC cron | 北京时刻 | 作用 |
|---|---|---|---|
| 锚点 | `45 15 * * 1-5` | 23:45 周一~周五 | 主锚点，睡到收盘 |
| 锚点 | `45 16 * * 1-5` | 00:45 周二~周六 | 备锚点，睡到收盘 |
| 尾点 | `10 20 * * 1-5` | 04:10 周二~周六 | 收盘后直接干 |
| 尾点 | `50 20 * * 1-5` | 04:50 | |
| 尾点 | `30 21 * * 1-5` | 05:30 | |
| 尾点 | `10 22 * * 1-5` | 06:10 | |
| 尾点 | `50 22 * * 1-5` | 06:50 | |
| 尾点 | `30 23 * * 1-5` | 07:30 | |
| 尾点 | `15 0 * * 2-6` | 08:15 | |
| 尾点 | `50 0 * * 2-6` | 08:50 | |
| 尾点 | `25 1 * * 2-6` | 09:25 | |
| 兜底 | `0 4 * * 2-6` | 12:00 | 早上全挂时中午补发 |
| 兜底 | `0 10 * * 2-6` | 18:00 | 最后一道，绝不静默 |

### 三个必须知道的时间坑

1. **星期写法分两段**。UTC 15:45 / 20:10 / 23:30 落在 UTC 周一到周五，跨过 00:00
   之后（00:15 / 00:50 / 01:25 / 04:00 / 10:00）就变成 UTC 周二到周六。两段合起来
   正好覆盖北京周二到周六的每个早上。
2. **北京周一早上不推送**。因为那时对应的美东是周日——不开市，推的会是上周五的
   重复数据。北京周一唯一的触发点是 23:45 的锚点，它服务的是美东周一的收盘。
3. **不能用「北京日期 −1」硬算美东日期**。夏令时切换让偏移在 12/13 小时之间跳。
   本脚本用 `zoneinfo` 换算，抓数窗口按美东 09:30 / 16:00 锚定，冬令时自动适配——
   2026-11-02 起美国进入冬令时，`wait_for_close.py` 会自动多睡 55 分钟，无需改配置。

## 抗漏发设计（2026-10-21 加固）

起因：A 股简报有一次早上没送达，排查发现是**单点 cron 被 GitHub 丢弃**——`schedule`
是 best-effort，高峰期会延迟，负载极高时直接不跑。而失败是静默的：没有任何提示，
只能靠自己发现「今天怎么没收到」。美股链路存在同样的风险，逐条补齐：

| 缺口 | 原来的行为 | 现在 |
|---|---|---|
| **cron 延迟 0.5~5.5 小时** | cron 设在 07:40，延迟 2 小时就跨过早上 8 点 | 提前排队 + 睡到收盘，容错从 20 分钟变 5 小时 |
| **cron 被静默丢弃** | 一旦丢了整天空窗 | 13 个触发点 + 当日闸门去重 |
| **行情接口全挂** | 判成「休市」，跳过推送且 run 显示成功 | 抛 `FatalFetchError` → run 变红 → 告警 → 下个触发点重试 |
| **接口返回陈数据** | 和休市无法区分，静默出一份错的 | 精确比对「上一个工作日」，不符即抛错 |
| **数据残缺** | 两三个板块也照样成稿 | 指数 < 4 或板块 < 6 直接失败 |
| **job 失败无人知** | 只在 GitHub 网页标红 | `if: failure()` 用 Bark 推告警，带失败环节与日志链接 |
| **Pages 部署失败** | 阻塞后续的手机推送 | 三步全部 `continue-on-error`，页面失败不影响送达 |
| **推送渠道全缺失** | 返回 0，run 显示成功 | 返回 1，触发告警 |

三条设计原则：

1. **送达优先于页面**。Pages 挂了只是链接内容不对，手机推送才是主目标，不能被它拖累。
2. **失败必须可见**。宁可误报一次让人去看一眼，也不要静默漏发。所有「看起来正常但其实没送出去」
   的路径都改成了硬失败。
3. **标记只在成功后写**。`data/sent.json` 由 `mark_done.py` 在 `notify.py` 之后写入。
   抓取阶段写的 `history.json` 不能当闸门用——否则推送失败但 history 已提交时，
   后续触发点会误判为已完成，等于彻底放弃当天补发。

## 链路

```
GitHub Actions (13 个 cron 触发点：锚点 23:45/00:45 + 尾点 04:10~09:25 + 兜底 12:00/18:00)
   │
   ├─ scripts/check_done.py    第一道闸门 → data/sent.json 已有今日则退出（约 10 秒）
   │
   ├─ scripts/wait_for_close.py 睡到美东 16:05（吸收 cron 队列延迟，最长 5h30m）
   │
   ├─ scripts/check_done.py    第二道闸门 → 睡眠期间可能已被其他触发点完成，复查一次
   │
   ├─ git pull --rebase        睡眠期间代码可能被更新过，先对齐，避免 push 被拒
   │
   ├─ scripts/fetch_brief.py   抓数据 → data/brief.json
   │    ├─ 腾讯行情    五大指数 / 11 个 GICS 板块 ETF / MAG7 / 宏观 ETF（单请求批量取）
   │    ├─ 外媒 RSS    WSJ 市场·美国商业 / CNBC 市场·科技·经济·头条 / MarketWatch / 美联储官网
   │    ├─ 机器翻译    Google 免费端点 → MyMemory 降级 → 仍失败保留英文原文
   │    ├─ Nasdaq 日历 明日财报（盘前/盘后 + EPS 预期）、明日美国经济数据（预期/前值）
   │    ├─ 国内源      仅在全部外媒不可用时兜底，不开天窗
   │    └─ data/history.json  SPY+QQQ 成交额（用于计算放缩量）
   │
   ├─ 交易日判定：用「行情时间的美东日期」对齐「应收盘日」，假日自动识别 → 休市直接退出
   │              接口故障 / 陈数据 → 抛错告警，不再伪装成休市
   ├─ scripts/build_brief.py   渲染 → dist/index.html（单文件、移动优先、深色）
   ├─ GitHub Pages             部署页面（失败不阻塞推送）
   ├─ scripts/notify.py        推送到手机（飞书 / Bark / Server酱 / PushPlus / Telegram）
   ├─ scripts/mark_done.py     写 data/sent.json 标记当日完成
   └─ scripts/alert.py         仅失败时触发，Bark 推送失败环节 + 日志链接
```

## 为什么改用外媒（2026-10-20 改造）

原先「要闻」和「展望」用国内财经源（东财 / 新浪），实测有四个问题：

1. **转述损耗**：一条英文报道经三家国内媒体转述，会出现三种不同的数字和口径。
2. **标题党**：国内标题常把「某分析师认为」写成「XX 要涨」，与原文性质不符。
3. **时滞**：美股收盘后 2–4 小时才有像样的中文稿，且彼此高度雷同。
4. **跑题**：国内快讯流混入大量 A 股内容，需层层过滤仍有漏网。

改为直读一手外媒。**GitHub Actions 跑在美国机房**，这些源天然可达，反而比本机更稳。

| 用途 | 原来（国内） | 现在（外媒） |
|---|---|---|
| 今日要闻 | 东财「美股收盘」+ 新浪快讯 | WSJ / CNBC / MarketWatch / 美联储官网 RSS |
| 明日展望 | 东财策略研报（多为 A 股视角的海外周报） | 外媒分析师观点 + **Nasdaq 明日财报/经济数据日历** |

**「明日事件」是这次改造里最有价值的部分**：财报日期、盘前/盘后时段、EPS 预期、经济数据预期值与前值——这些是**确定要发生的事实**，比任何"机构展望"都可靠。

页面上的英文原题同时保留：中文是机器翻译，原文可供核对，避免译错被当成事实。

### 三层过滤（防外媒噪声）

外媒 RSS 同样有噪声（社会新闻、个人理财专栏、评论秀），因此设三道闸：

1. **市场相关性闸门**：标题必须落在市场/产业语汇里；公司名单独出现不算，需叠加商业动作词（announce / earnings / beat / guidance…）。这一条挡掉了「OpenAI 窃听案嫌疑人」这类含公司名但无关市场的新闻。
2. **噪声词黑名单**：newsletter / Investing Club / Jim Cramer 个人节目 / Musk 送股 等。
3. **分数门槛**：低于门槛不凑数，宁可只出 2 条。


## 板块设计：与 A 股版哪里不同

A 股版看「指数分化 + 量能 + 题材轮动」；美股的结构不同，所以变量换了三处：

| 变量 | A 股版 | 美股版 | 为什么换 |
|---|---|---|---|
| 板块 | 东财概念板块（几百个） | 11 个 GICS 行业 SPDR ETF | 美股没有「概念板块」等价物，行业 ETF 才是机构真实的仓位语言 |
| 广度 | 上涨家数（交易所收评披露） | RSP（标普等权）− SPY（市值加权） | 美股无公开涨跌家数接口。等权与市值加权的差值，能直接量化「指数是不是几只巨头抬出来的」 |
| 波动 | 成交额放缩 | 标普日内振幅 + 成交额放缩 | VIX 的中文实时源不可得（腾讯 usVIX 停在 2026-09），日本内振幅更可靠 |
| 特有 | — | **MAG7 权重股** | 七巨头是美股指数方向的直接决定者，必须单列 |

## 简报版块（页面自上而下）

| 序号 | 板块 | 内容 |
|---|---|---|
| 1 | 指数条 | 道指 / 纳指 / 标普500 / 罗素2000 / 费半 + 振幅 + 广度 + 成交额，合并为一条信息带 |
| 2 | 板块强弱 | 11 个 GICS 行业 ETF 涨跌分列条形可视化（涨红左对齐、跌绿右对齐） |
| 3 | 权重股 MAG7 | 七巨头涨跌幅 + 均值较标普的高低 |
| 4 | 盘面归因 | 结构 / 广度 / 量能 / 主线 / 催化 / 宏观 六段判断 |
| 5 | 今日要闻 | 最多 3 条外媒一手报道：中文标题 + **英文原题** + 摘要 + 原文链接 |
| 6 | 明日事件 | 财报名单（盘前/盘后 + EPS 预期）、美国经济数据（预期/前值） |
| 7 | 明日展望 | 外媒分析师观点；外媒缺失时降级中文研报并明确标注 |

**归因的原则**（沿用 A 股版）：数字只在顶部出现一次，归因段落只给判断、不复述数字；因果关系一律标注为「相关性对齐，不能直接认定为涨跌原因」。抓不到研报时明确写"不做方向性判断"，不用模板话术填充。

红涨绿跌（与 A 股简报一致，降低两套简报间的认知切换成本）。

## 已知边界

- **GitHub Actions cron 有 5–20 分钟延迟**，07:40 触发通常 07:45–08:00 出结果。
- **美东假日自动识别**：靠「行情日期 vs 应收盘日」对齐判断，不需要维护假日表；误判风险只在行情接口挂掉时出现，那时会直接报"未取到行情"而不是硬编一份简报。
- **要闻可能只有 2 条**：设了最低分门槛，低于门槛的不用来填满 3 条。
- **翻译是机器翻译**：Google 免费端点优先，不通则降级 MyMemory（匿名额度约 5000 字符/天），再不通就保留英文原文。因此页面同时给出英文原题，便于核对。
- **WSJ / MarketWatch 偶有 0 条**：这两家的 RSS 缓存更新慢，窗口内可能确实没有新条目，属正常。
- **资讯窗口两端封口**：起点美东 09:30 前 1 小时、终点美东 20:00。不封口会把「今天下午的新闻」错配给「昨晚的行情」——这是设计时刻意防的一个坑。
- 数据源均为公开接口，上游限流或改版会降级（缺条不编造）。
- **GitHub 60 天无提交会自动停用定时工作流**：本项目每日回写 `data/history.json`，天然规避。

## 部署（首次，约 3 分钟）

```bash
GH_TOKEN=github_pat_xxx BARK_URL=https://api.day.app/你的Key python3 scripts/deploy_github.py
```

脚本会自动：建仓库 → 上传全部文件 → 开启 Pages（Source = GitHub Actions）→ 写入 `BARK_URL` Secret → 触发一次运行。

**Token 必须带 `repo` + `workflow` 两个权限**。只给 `repo` 时，写入 `.github/workflows/*` 会返回 **404**（伪装成"文件不存在"），看起来像环境问题，实际是权限问题。

推送渠道（可多配，写在仓库 Settings → Secrets and variables → Actions）：

| Secret | 渠道 | 怎么拿 |
|---|---|---|
| `FEISHU_WEBHOOK` | 飞书 | 群 → 设置 → 群机器人 → 添加自定义机器人 → 复制 Webhook |
| `BARK_URL` | Bark（iOS，最省事） | App Store 装 Bark → 复制形如 `https://api.day.app/你的Key` |
| `SCT_KEY` | Server酱（微信） | sct.ftqq.com 微信扫码 |
| `PUSHPLUS_TOKEN` | PushPlus（微信） | pushplus.plus 微信扫码 |
| `TG_BOT_TOKEN` + `TG_CHAT_ID` | Telegram | @BotFather 建 bot，@userinfobot 取 chat id |
